The big picture

The browser talks to only one thing: the API Gateway. The gateway checks the login token, checks the user's role, and forwards the request to the right internal service. Internal services can't be reached from outside the cluster. All services use one MongoDB database, and each service owns its own collection.

The only way in from outside is the Ingress (NGINX Ingress Controller). It forwards to the API Gateway, whose Service is internal (ClusterIP) like every other service.

API Gateway

port 4000APIGateway_Microservice/api-gateway.js, load-balancer.js

The app's front door. Every request reaches it through the Kubernetes Ingress (browser → Ingress → gateway), and it checks the token and role, forwards to the right service, load-balances door swipes, and serves the web dashboard.

What it does to each request

  1. Strips any X-User-* headers the client sent.
  2. Logs the request (to the console and the shared log volume). Health probes are skipped.
  3. Verifies the JWT (HS256, signature + expiry). Missing token: 401, bad token: 403.
  4. Checks the role against a rule table for that route. Wrong role: 403.
  5. Adds trusted headers X-User-Id/Email/Role/Name/Department and proxies with http-proxy (keep-alive connections).

Route rules (summary)

  • /reg, /login: public
  • /api/rooms: read all roles. Enrollment request: student. Approve/reject/remove student and lock toggle: admin + faculty. Every other write: admin.
  • /api/permissions, /api/admin: admin
  • /api/students: student · /api/teachers: faculty
  • /api/logs: swipe and own history for all roles, the rest admin
  • /api/alerts: report and active for all roles, the rest admin

Round-robin load balancer (load-balancer.js)

Every 5 seconds the gateway asks Kubernetes DNS for access-log-headless. That's a headless Service, so DNS returns one IP per ready Access Log pod. The gateway keeps that list and sends swipe #1 to pod A, #2 to pod B, #3 to pod A… The counter keeps going even when the list changes. Each pod returns its name in X-Served-By-Instance, so the stats and the dashboard show real pod names. If DNS fails, the last known list is kept. Outside Kubernetes it uses a fixed URL list instead.

Changed for the final

  • Fixed leftover merge-conflict lines that stopped the gateway from starting.
  • Security fix: header stripping. Before, anyone could send X-User-Role: admin on public routes.
  • No hard-coded fallback JWT secret: it refuses to start without a 32+ character secret.
  • Midterm: two hard-coded instances on ports 5005/5015. Final: automatic pod discovery, so scaling and autoscaling just work.
  • Long if-chains became an ordered rule table (routeByRules). Gateway rules now match what each service allows.

Likely questions

Kubernetes Services already load-balance. Why build your own?

A normal Service spreads connections roughly at random. Ours is strict round-robin per request and records per-pod counts we can show live. The headless Service gives us the pod list, so we keep the Kubernetes benefits (only ready pods, automatic scaling) and still control the algorithm.

What happens if an Access Log pod crashes mid-demo?

Its readiness check fails, so it drops out of DNS. Within about 5 seconds the gateway stops sending to it. Meanwhile the Deployment starts a replacement, which joins the rotation once ready.

Why should services trust the X-User headers?

Three layers. The gateway deletes any copies a client sends. The services have no outside-facing Service. And NetworkPolicies block every pod except the gateway from reaching them, so even a pod inside the cluster can't call a service with forged headers. We tested it: an unlabeled pod times out, the gateway gets through.

What would production add?

Mutual TLS between pods (a service mesh like Istio or Linkerd), so traffic is encrypted and each side proves its identity cryptographically, not just by network rules.

Web dashboard (UI)

served by the gateway at /APIGateway_Microservice/public/index.html

One web page, served by the API Gateway, laid out like the university's Canvas: a dark blue side menu, big page titles, and one page per task. Every role uses it to log in, manage rooms, swipe badges, watch the load balancer, and trigger lockdowns.

What's on it

  • Side menu (like Canvas): Account, Dashboard, Badge reader, Rooms, Classes, plus Users and Checks for admins or Profile for students and faculty. Each item opens its own page, so nothing is one long scroll. The Dashboard has Canvas-style course cards linking to each page.
  • Searchable dropdowns for every choice field (room, who to swipe as, classroom, instructor email, student email, role filter): click to see all stored values, or type to filter.
  • Login and sign-up screens, plus quick buttons for the three demo accounts. Sign-up only offers Student or Faculty.
  • Room inventory with lock/unlock buttons. Admins see admin actions, faculty see lock controls for their own rooms, students see read-only clearance info.
  • Classroom portals: students request enrollment, faculty approve/reject, admins assign teachers and enroll students directly.
  • Badge reader: Swipe badge and Swipe 4 times, a reader that shows Granted or Denied with the reason, and the response headers. Admins can pick who to swipe as (any registered person) to demo a student or teacher being let in or denied; students and faculty always swipe as themselves.
  • Live load-balancer panel: one card per Access Log pod, named after the real pod, with request counts and percentages. The pod that served the last swipe is highlighted.
  • Emergency banner and lockdown buttons (lockdown buttons admin only).
  • Profile portal: student or teacher profile and room schedule, from the Student/Teacher services.
  • Admin user directory and a built-in Run system checks button (admin only).

How it works

  1. On login it stores the JWT in sessionStorage (cleared when the tab closes).
  2. Every API call sends Authorization: Bearer <token> to the gateway. The page talks to nothing else.
  3. applyRolePermissions(role) shows or hides panels for admin, faculty or student, and the menu only lists pages that role may open (typing an admin page's URL as a student lands on Dashboard).
  4. Pages are switched in the browser by the URL fragment (#rooms, #classes…), so there's no page reload and the back button works.
  5. The searchable dropdowns wrap the original <select>, which stays the source of truth, so all existing code that reads .value works unchanged.
  6. Load-balancer cards come from the X-Served-By-Instance header on each swipe; for admins, also from /api/gateway/load-balancer-stats.
  7. Data from the server is passed through escapeHtml() before it's shown, so a room or user name can't inject HTML or scripts.

Changed for the final

  • Redesigned to match the university's Canvas: side menu, separate pages per role, Canvas-style dashboard cards, Lato font.
  • Every choice field became a searchable dropdown; "Swiping as" became a real picker for admins.
  • The load-balancer panel used to have two fixed cards (Instance-1 and Instance-2). Now it draws one card per real pod, so scaling to 3 pods shows 3 cards.
  • The "Admin" option was removed from public sign-up, and the demo auto-register no longer creates admins (admin comes from the Kubernetes Secret).
  • Removed an unused switchUserRole function that registered admin accounts publicly.
  • The built-in test runner now reports real PASS/FAIL (it used to always say "All Checks Passed") and checks that public admin sign-up is blocked.

Likely questions

If the UI hides admin buttons, is that the security?

No. Hiding buttons is only for convenience. The real checks happen on the server: the gateway and each service verify the token and role on every request. A student who calls an admin API directly with Postman still gets 403.

Why does the gateway serve the UI instead of a separate web server?

The page and the API share one address (same origin), so there are no cross-origin problems and only one Service is exposed. For a bigger app you'd put the UI in its own container or a CDN.

How does the UI know which pod answered?

Each Access Log pod adds its own pod name in the X-Served-By-Instance response header (Kubernetes injects the name as POD_NAME). The page reads that header after every swipe.

Why sessionStorage and not a cookie?

It keeps the token per tab and simple for a demo. A production app would usually use an HttpOnly cookie, so page scripts can't read the token if there's ever an XSS bug.

Permission service

port 5004Permission_Microservice/index.js

Admins grant a user access to a specific room on specific weekdays and hours, for a limited time. Every endpoint is admin-only.

MethodPathWhat it does
POST/api/permissions/grantGrant access, or update the existing grant for the same email + room. Defaults: Mon–Fri, 08:00–20:00, valid 1 year.
GET/api/permissionsList all grants (filter by role, room, active).
GET/api/permissions/user/:idActive grants for one user (ID or email).
GET/api/permissions/room/:idWho is allowed into one room.
POST/api/permissions/checkSimulate the door decision for any user, room and time (timestamp lets you test e.g. Sunday 23:00).
DELETE/api/permissions/:idRevoke a grant.

Validation on grant

  • allowedDays must be real weekday names.
  • Times must be HH:mm and different. Start later than end means overnight (e.g. 22:00–02:00).
  • validUntil must be in the future.
  • grantedBy is the admin's email from the token (can't be faked).

The time-window rule (shared/access-rules.js)

  1. Before validFrom → NOT_YET_VALID
  2. After validUntil → PERMISSION_EXPIRED
  3. Today not in allowedDays → OUTSIDE_ALLOWED_DAYS
  4. Time outside start–end → OUTSIDE_SCHEDULED_HOURS (overnight windows wrap past midnight)
  5. Otherwise → AUTHORIZED

Changed for the final

  • The time-window logic was duplicated in Permission and Access Log. Now both call one shared function, so they can never disagree.
  • The gateway now matches the service: /check is admin-only on both (before, the gateway let students through but the service rejected them).
  • Two database indexes (userId+roomId, userEmail+roomNumber) keep door lookups fast.
  • Overnight windows are now supported (they used to be rejected).

Likely questions

Where is a permission actually enforced?

At the door: the Access Log service reads access_permissions on every swipe and applies the same shared rule. Permission is where grants are managed. Access Log is where they're used.

Why compare times as strings?

Times are zero-padded HH:mm, so text order equals time order ("08:05" < "20:00"). It's simple and correct for same-day windows.

Can a permission cover a night shift, like 22:00–02:00?

Yes. If start is later than end, it's treated as an overnight window. The after-midnight part counts as the previous day, so "Friday 22:00–02:00" lets you in at Saturday 01:30 but not Saturday 03:00. Tests 8.1–8.4 prove it.

Any limitation?

Times use the server's clock and time zone. A multi-campus system would store a time zone per building.

Emergency Alert service

port 5006EmergencyAlert_Microservice/index.js

Admins lock down the whole campus or one building, and anyone can report a security incident.

MethodPathWhoWhat it does
POST/api/alerts/lockdownadminCreate a CAMPUS_LOCKDOWN (building ALL) or BUILDING_LOCKDOWN alert, then set isEmergencyLocked = true on every matching room.
POST/api/alerts/liftadminResolve every active lockdown alert for that building (or all of them for ALL) and set isEmergencyLocked = false on those rooms. Lifting by alertId uses that alert's building.
GET/api/alerts/activeeveryoneIs there an emergency right now? Drives the red banner in the UI.
POST/api/alerts/reporteveryoneReport an incident (suspicious activity, door tamper, fire hazard…).
GET/api/alerts/historyadminAll alerts, newest first (filter by status, severity; max 500).
DELETE/api/alerts/:idadminDelete an alert.

How lockdown reaches the doors

Emergency writes the isEmergencyLocked flag straight onto the room documents. On every swipe, Access Log checks that flag first, before anything else, so even admins and enrolled students are denied with CAMPUS_EMERGENCY_LOCKDOWN.

Alert fields

alertType, building, severity (LOW → CRITICAL), status (ACTIVE / RESOLVED), triggeredBy, resolvedBy, timestamps.

Changed for the final

  • triggeredBy / resolvedBy now come from the logged-in user's token. Before, the request body could claim anyone.
  • A student report can't create a lockdown-type alert. It's converted to SUSPICIOUS_ACTIVITY.
  • The building name is escaped before it's used in a database search (prevents regex injection).
  • Lift used to resolve only one alert while unlocking every room, so other lockdowns still showed ACTIVE. Now it resolves all the lockdowns it covers, and incident reports stay open.
  • Reopening one building during a campus-wide lockdown is refused (409). Lift ALL first.
  • Admin-only routes are checked inside the service as well as at the gateway.

Likely questions

Why does Emergency update the rooms collection directly instead of calling the Room service?

Speed and reliability in an emergency: one database update locks every room even if the Room service is down. The trade-off is that two services write to rooms. A stricter design would publish a "lockdown" event that Room handles.

Can a faculty member trigger a lockdown?

No. Before the fix they could, through a Room-service route the gateway allowed for faculty. Now that route is admin-only, and run_tests.js check 6.2 proves it returns 403.

What if there are several lockdowns at once?

Lifting ALL resolves every one of them. Lifting one building resolves only that building's lockdowns, and it's refused while a campus-wide lockdown is active, so you can't accidentally reopen part of a locked campus. Tests 9.1–9.3 cover this.

Registration service

port 5001Registration_Microservice/registration.js

Creates user accounts and gives admins user-management tools. It also creates the first admin account when the system starts.

MethodPath (through gateway)WhoWhat it does
POST/reg, /api/auth/registeranyoneSign up as student or faculty. Admin role only if the caller sends an admin token.
POST/api/admin/api/auth/batch-registeradminImport up to 500 users at once. Each row reports CREATED / SKIPPED / FAILED.
GET/api/admin/usersadminList users (filter by role, department). Passwords never returned.
GET/api/admin/users/:id, /users/card/:cardIdadminLook up one user by ID or by badge card ID.
DELETE/api/admin/users/:emailadminDelete a user (an admin can't delete themselves).

How sign-up works

  1. Checks name, email format, password is 8+ characters, and role is valid.
  2. Blocks admin unless the gateway says the caller is an admin (403 otherwise).
  3. Returns 409 if the email already exists.
  4. Hashes the password with bcrypt (10 rounds), so the plain password is never stored.
  5. Generates USR-… ID and a badge CARD-######, then saves to users.

Bootstrap admin

When the service connects to MongoDB, it reads ADMIN_EMAIL / ADMIN_PASSWORD from the Kubernetes Secret and creates that admin if it doesn't exist. If two replicas try at once, MongoDB's unique email index rejects the duplicate (error 11000) and the code ignores it.

Kubernetes

Deployment + ClusterIP Service. It's the only service that receives the ADMIN_* secret keys.

Changed for the final

  • Security fix: before, anyone could register as admin from the public sign-up form. Now only student/faculty can.
  • The admin routes now check the role inside the service too, not just at the gateway.
  • The batch import's shared default password CampusDefaultPass123! was removed; each user needs their own.

Likely questions

Why hash passwords with bcrypt instead of encrypting them?

Hashing is one-way: even we can't recover the password. bcrypt is deliberately slow and adds a random salt, so two identical passwords give different hashes and brute-forcing is expensive.

How does a new admin get created then?

An existing admin calls /reg with their token and role: admin. The very first admin comes from the Kubernetes Secret at startup.

How does Registration know who is calling if the route is public?

The gateway uses "optional auth" on /reg: if a valid token is present it forwards the user's role, otherwise the caller is treated as anonymous.

Why is registration separate from authentication?

Different jobs, different load: sign-ups are rare, logins are constant. Splitting them lets each scale and change independently. That's the single-responsibility idea behind microservices.

Authentication service

port 5002Authentication_Microservice/authentication-service.js

Checks email + password and issues a signed JWT that proves who you are for the next 8 hours.

MethodPathWhat it does
POST/login, /api/auth/loginEmail + password (optional role) → token + user info. Wrong details: 401. Suspended account: 403.
POST/api/auth/verifyChecks a token and returns its decoded contents.

What's inside the token

id, email, name, role, department, cardId, plus issue time and expiry. Signed with JWT_SECRET using HMAC-SHA256. Anyone can read a JWT, but nobody can change it without the secret.

Security details

  • Same error message for "no such email" and "wrong password", so attackers can't discover accounts.
  • An unknown email still runs a bcrypt compare against a dummy hash, so response time doesn't reveal whether the email exists.
  • The JWT_SECRET exists only in this service and the gateway (least privilege).

Changed for the final

  • Removed the hard-coded fallback secret. The deploy script generates a random 48-character key per cluster.
  • Token lifetime is 8 h (configurable with JWT_EXPIRES_IN). It used to be 24 h.
  • Added the timing-attack fix described above.

Likely questions

Why JWT instead of sessions?

It's stateless: the gateway verifies the signature itself, without a session store or a call to Authentication on every request. That's why any replica can handle any request.

How do you log out or revoke a token?

The UI deletes it from the browser. Server-side revocation would need a blocklist or short tokens plus refresh tokens. That's a known JWT trade-off, so we keep tokens to 8 h.

Where is the secret stored?

In a Kubernetes Secret, injected as an environment variable. It's never in the code or the image.

Access Log service (door swipes)

port 5005 · 2–5 podsAccessLog_Microservice/index.js

Decides whether a door opens when a badge is swiped, and writes every decision to an audit log. This is the busiest service, so it's the one that scales.

The door decision, in order (first match wins)

  1. Room is under emergency lockdownDENIED · CAMPUS_EMERGENCY_LOCKDOWN
  2. Room is physically lockedDENIED · ROOM_PHYSICALLY_LOCKED
  3. User is adminGRANTED
  4. Faculty assigned to this classroomGRANTED
  5. Student enrolled in this classroomGRANTED
  6. Has an access permission (checks days, hours, dates)GRANTED / DENIED reason
  7. GENERAL room with no instructor assigned (open space)GRANTED
  8. Anything elseDENIED · NOT_ENROLLED / NOT_ASSIGNED
MethodPathWhoWhat it does
POST/api/logs/swipeallSwipe a badge at a room. Users always swipe as themselves. Admins may simulate another user.
GET/api/logs/user/:idallLast 50 swipes for a user. Non-admins can only read their own.
GET/api/logsadminAudit log with filters (status, room, user, role; max 1000).
GET/api/logs/stats/summaryadminTotals, approval rate, denial reasons, top 5 rooms (5 queries run in parallel).
DELETE/api/logs/cleanupadminDelete logs older than N days (default 90).

Changed for the final

  • Restored classroom access (steps 4, 5 and 7). A merge had deleted it, so enrolled students were being denied.
  • Security fix: the user's identity comes from the token. Before, a student could send userRole: "admin" in the body and open any door.
  • Students can no longer read other people's swipe history.
  • One Deployment with replicas, an autoscaler (HPA) and a PodDisruptionBudget, instead of two separate copies. The instance name is the pod name, injected by Kubernetes.

Likely questions

Why is this the service that scales?

Every door swipe on campus hits it, so it gets the most traffic. It's stateless (all data is in MongoDB), so extra pods can run side by side safely.

How does autoscaling work?

The HPA watches average CPU. Above 60% it adds pods (max 5), and when load drops it removes them (min 2). It needs metrics-server, which the deploy script installs with -InstallMetricsServer.

What's the PodDisruptionBudget for?

It keeps at least 1 Access Log pod running during planned maintenance (like draining a node), so doors never stop working.

How does enrollment affect the door?

Why store rosters inside the room document?

One read answers "is this person in this class?", which is exactly what the door needs. It's fine for class sizes. For huge rosters a separate enrollments collection would scale better.

How deployment works

Publishing (Sokhadom, after a code change): scripts\build-images.ps1 -Registry sokhadum -Push builds the 9 images from the repository root (so they include shared/), gives the build a unique tag like build-20261118-170528, pushes them to Docker Hub as public sokhadum/smart-campus-<service> images, and points k8s/*.yaml at that exact tag. The updated YAML then goes to GitHub.

Deploying on any laptop (two ways):

  1. From Docker Hub (normal way): scripts\deploy.ps1 -UseDockerHub applies the YAML as committed, and Kubernetes downloads the pinned images from Docker Hub. No building needed, but it needs internet.
  2. Build locally (offline backup): scripts\deploy.ps1 builds the images on the laptop and loads them into the cluster (on Docker Desktop's kind mode the cluster can't see docker build images, so they're imported into the node; minikube and kind have their own loaders). It rewrites the YAML to use those local images.

Either way, deploy.ps1 then creates the Secret (random JWT key, bootstrap admin), applies every manifest, and waits until all pods are ready. scripts\open-app.ps1 opens the app through the Ingress if the cluster doesn't publish it on localhost; scripts\dashboard.ps1 opens the Kubernetes Dashboard.

Likely questions

What does the Ingress do, and why not just a LoadBalancer Service?

The Ingress is an HTTP router at the edge of the cluster: one entry point with rules by host name and path (here localhost and smartcampus.local → the gateway). A LoadBalancer gives each Service its own external address; an Ingress lets many apps share one, adds host/path routing and is where TLS would go. So our app Services are all internal (ClusterIP) and the Ingress is the only door.

Ingress vs Ingress Controller?

The Ingress is just the rules (our YAML). The Ingress Controller is the program that follows them: an NGINX pod in the ingress-nginx namespace. Without a controller an Ingress does nothing. deploy.ps1 installs it.

So the request goes through two "gateways"?

Yes, with different jobs. The Ingress is the cluster's network door (HTTP routing). The API Gateway is the app's door (JWT check, roles, round-robin to Access Log pods). Path: browser → Ingress → API Gateway → service.

Where do the images come from?

All 9 are published on Docker Hub as public images, sokhadum/smart-campus-<service>, and the YAML points at one pinned build tag, so every laptop runs identical code. deploy.ps1 -UseDockerHub makes Kubernetes download them. build-images.ps1 -Registry sokhadum -Push publishes a new version. Without -UseDockerHub the script builds locally, which works offline as a backup.

Why pin a build tag instead of :latest?

latest changes every time someone pushes, so two laptops could run different code with the same YAML. A pinned tag like build-20261118-170528 always means the same image, and rolling back is just pointing at an older tag.

Why the unique image tag?

Kubernetes only re-pulls an image when the tag changes. With the same :local tag, a rebuilt image would be ignored and old code would keep running. We hit exactly that while testing.

Why is the gateway's update strategy "Recreate"?

Its log volume is ReadWriteOnce (one pod at a time), so the old pod must stop before the new one starts.

Are Kubernetes Secrets encrypted?

By default they're only base64-encoded in etcd, not encrypted. Production clusters enable encryption at rest or use a vault. For this demo, the point is that secrets are out of the code and images.

Questions anyone might get

Why microservices instead of one app?

Each service can be developed, deployed, scaled and restarted on its own. We scale only Access Log because it's the busy one. A crash in Emergency doesn't take down login.

Why an API gateway?

One entry point: authentication and role checks happen once, internal services stay hidden, and the browser needs one address instead of nine.

What changed from midterm to final?

EC2 + Docker Compose became Kubernetes. Two fixed Access Log copies became an autoscaled Deployment discovered through DNS. MongoDB runs inside the cluster with persistent storage. We added health probes, resource limits, non-root containers, Secrets, NetworkPolicies, and the security fixes (header spoofing, public admin sign-up, faculty lockdown, swipe impersonation). Duplicated code moved into shared/.

What if MongoDB goes down?

Each service's /health starts returning 503, so Kubernetes stops sending traffic to it (readiness). The process stays alive (liveness), and Mongoose reconnects automatically when the DB returns.

Isn't sharing one database against microservice rules?

Strictly, each service should own a private database. We use one database with one collection per owning service, which keeps the project simple. The cost: a few services read others' collections directly (Access Log reads rooms and permissions). Fixing that would mean API calls or events between services.

How do you know it works?

node run_tests.js runs 35 checks: registration, login, roles, bad tokens, round-robin across pods, the four security fixes, enrollment-based door access, overnight permissions, and lockdown lifting. The dashboard also has a built-in verification button.
